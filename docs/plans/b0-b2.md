# ZapResponse B0–B2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Override do projeto (spec.md §0.2):** este plano **não tem passos de commit**. Onde uma skill pedir commit, atualize `docs/progress.md` e siga. Nenhum comando git que altere estado.

**Goal:** Entregar o esqueleto do monorepo, o núcleo do servidor Fastify e o schema Postgres do ZapResponse, com `check`/`lint`/`test`/`build` verdes e migrations + seed rodando do zero.

**Architecture:** Monorepo npm workspaces com `apps/server` (Fastify 5 + Zod 4 + Pino 10 + Drizzle) e `packages/contracts` (schemas Zod compartilhados). TypeScript com **project references** (`tsc -b`), então um único comando resolve a ordem contracts → server e emite os `.d.ts`. O servidor é construído por `buildApp(opts)` para que os testes usem `app.inject()` sem abrir porta. Dois Postgres em Docker: dev (5432) e test (5433). Nenhuma tabela comercial existe sem `organization_id`, e o vínculo lead↔organização é garantido por FK composta no banco, não só por código.

**Tech Stack:** Node 24 · TypeScript 6.0.3 · Fastify 5.12.7 · Zod 4.6.7 · fastify-type-provider-zod 7.0.0 · Pino 10.4.0 · Drizzle ORM 0.45.4 + drizzle-kit 0.31.11 · pg 8.23.1 · Vitest 5.0.5 · ESLint 10.13.0 + typescript-eslint 8.72.0 · Prettier 3.9.10 · PostgreSQL 18 (Docker)

**Spec:** [`spec.md`](../../spec.md) — §0 (regras invioláveis), §1 (decisões e estrutura), §4 fases B0, B1, B2. Decisões de versão: [`docs/decisions.md`](../decisions.md).

## Global Constraints

- **Nenhum git que altere estado.** Só `status`, `diff`, `log`, `show` (spec §0.1).
- **Versões fixadas** exatamente como em `docs/decisions.md`. Não inventar versão nem API; conferir o pacote instalado antes de usar um export.
- **TypeScript 6.0.3**, não 7.x: `typescript-eslint@8.72.0` tem peer `typescript: ">=4.8.4 <6.1.0"` (motivo completo em `docs/decisions.md`).
- **TypeScript strict** e, além dele: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`.
- **Scripts obrigatórios na raiz** (spec §1), que precisam existir de verdade porque o agente `test-verifier` roda exatamente estes: `check`, `lint`, `test`, `build`, `db:generate`, `db:migrate`, `db:seed`, `dev:server`.
- **Formato único de erro da API:** `{ "error": { "code", "message", "details"? } }`. Nunca stack trace, caminho de arquivo ou segredo na resposta; o detalhe técnico vai para o log.
- **`organizationId` nunca vem do cliente.** Toda função de repositório recebe `organizationId` obrigatório na assinatura.
- **Datas em UTC** no banco (`timestamptz`); a API fala ISO 8601.
- **Telefone** armazenado normalizado em E.164 com foco BR.
- **Nada é "pronto"** sem saída verde de `npm run check && npm run lint && npm run test && npm run build`.
- **Escopo congelado:** fora do escopo vai para `docs/backlog.md`, não para o código.
- **Sem exclusão física de `users` e `memberships` na v1.** Desligar um membro é mudar o estado da membership, nunca `DELETE`. As FKs compostas de `assignedTo`/`createdBy` contra `memberships` são `NO ACTION` de propósito: um `DELETE` falharia em vez de órfanar ou desatribuir silenciosamente. Quem precisar de exclusão real desatribui os leads no serviço primeiro (B4).
- **O banco de teste é identificado pelo nome.** Nenhum helper de teste roda `TRUNCATE` sem antes confirmar que o nome do banco na URL termina em `_test`.
- **A única fonte de requisito disponível é o `spec.md`.** O documento do produto (PDF v1.0), citado pelo spec em "seção 8" e "seção 12", não está no repositório. Onde o spec não detalhar um campo, decida pelo spec e registre em `docs/decisions.md`; não invente requisito.

## Review Focus

Classes de entrada que o spec implica mas cujo comportamento nenhum requisito descreve explicitamente. Cada linha tem um teste atribuído à tarefa que é dona do código.

1. **Rota inexistente** devolve o formato de erro padrão, não o 404 cru do Fastify — quem integra faz parse de uma forma só. → Tarefa 4a.
2. **Body acima do `bodyLimit`** devolve 413 no formato padrão, não a resposta interna `FST_ERR_CTP_BODY_TOO_LARGE`. → Tarefa 4a.
3. **`CORS_ORIGINS` vazio ou malformado** não pode virar "liberar qualquer origem": na ausência de origens configuradas o app não sobe. → Tarefa 3.
4. **Limite de requisições estourado** devolve 429 no formato padrão. → Tarefa 4b.
5. **Banco indisponível** no `/health` devolve 503 e uma mensagem genérica — nunca a string de conexão, que contém usuário e senha. → Tarefa 5.
6. **Suíte de testes apontada para o banco de desenvolvimento** destrói dados reais: `resetDb()` trunca. A ausência de `DATABASE_URL_TEST` tem de ser um erro alto, não um fallback silencioso para a porta 5432. → Tarefas 2 e 9.
7. **Histórico atribuído a usuário de outra organização:** `createdBy`/`completedBy` precisam da mesma FK composta contra `memberships` que o `assignedTo`, senão a identidade vaza entre tenants pelo histórico. → Tarefa 7b.

- [ ] **Step 1: Criar `package.json` na raiz**

`private: true`, `type: "module"`, `engines.node: ">=24"`, `workspaces: ["apps/*", "packages/*"]`.

Scripts, exatamente estes nomes (spec §1):

```json
{
  "check": "tsc -b",
  "lint": "eslint .",
  "pretest": "tsc -b packages/contracts",
  "test": "vitest run",
  "build": "tsc -b --force",
  "db:generate": "tsc -b packages/contracts && npm run db:generate -w @zapresponse/server",
  "db:migrate": "tsc -b packages/contracts && npm run db:migrate -w @zapresponse/server",

  "dev:server": "tsc -b packages/contracts && npm run dev -w @zapresponse/server"
}
```

`check` é `tsc -b` (incremental) e `build` é `tsc -b --force`: com project references, `tsc -b` é a checagem de tipos **e** a emissão dos `.d.ts`/`dist`, mas um `tsc -b` incremental rodando logo depois do `check` não verificaria nada e reportaria sucesso vazio. O `--force` faz do `build` uma verificação real. Os dois nomes existem porque o `test-verifier` roda os dois.

Todo script que carrega código que importa `@zapresponse/contracts` compila o pacote antes, porque o `exports` dele aponta só para `dist`: `pretest` (o npm o roda sozinho antes do `test`, então `npm run test` continua funcionando como comando único), os três scripts de banco e o `dev:server`.

```ts
import { describe, expect, it } from 'vitest';
import { parseEnv } from '../src/env.js';

const valid = {
  NODE_ENV: 'test',
  PORT: '3000',
  DATABASE_URL: 'postgres://zap:zap@localhost:5433/zapresponse_test',
  BETTER_AUTH_SECRET: 'a'.repeat(32),
  BETTER_AUTH_URL: 'http://localhost:3000',
  CORS_ORIGINS: 'http://localhost:3001, http://localhost:3002',
  LOG_LEVEL: 'silent',
};

describe('parseEnv', () => {
  it('converte PORT para número', () => {
    expect(parseEnv(valid).PORT).toBe(3000);
  });

  it('divide CORS_ORIGINS por vírgula e remove espaços', () => {
    expect(parseEnv(valid).CORS_ORIGINS).toEqual([
      'http://localhost:3001',
      'http://localhost:3002',
    ]);
  });

  it('rejeita CORS_ORIGINS vazio em vez de liberar qualquer origem', () => {
    expect(() => parseEnv({ ...valid, CORS_ORIGINS: '' })).toThrow();
    expect(() => parseEnv({ ...valid, CORS_ORIGINS: ' , ' })).toThrow();
  });

  it('exige DATABASE_URL', () => {
    const { DATABASE_URL: _omitido, ...semBanco } = valid;
    expect(() => parseEnv(semBanco)).toThrow();
  });

  it('rejeita BETTER_AUTH_SECRET curto', () => {
    expect(() => parseEnv({ ...valid, BETTER_AUTH_SECRET: 'curto' })).toThrow();
  });

  it('rejeita NODE_ENV desconhecido', () => {
    expect(() => parseEnv({ ...valid, NODE_ENV: 'staging' })).toThrow();
  });
});
```

- [ ] **Step 1: Definir as três tabelas**

Mesma convenção da Tarefa 7a: `snake_case` no banco, `camelCase` no TypeScript, PK `uuid` com `defaultRandom()`, `createdAt`/`updatedAt` como `timestamp({ withTimezone: true })` com `defaultNow().notNull()`, tudo em UTC.

`leads`: `id`, `organizationId` (notNull, FK cascade), `name` (notNull), `phone` (notNull, E.164 pela Tarefa 6), `email`, `source`, `status` (enum, notNull, default `'new'`), `assignedTo` (`uuid`, nullable), `notes`, `createdAt`, `updatedAt`.

`activities`: `id`, `organizationId` (notNull), `leadId` (notNull), `type` (enum, notNull), `body` (text, nullable), `payload` (`jsonb`, nullable — guarda `{ from, to }` do `status_change` da B4), `createdBy` (`uuid`, nullable), `createdAt`.
Sem `updatedAt`: atividade é registro de log, imutável depois de criada. O spec `spec.md:196` diz "+ `createdAt`/`updatedAt`" de forma genérica; esta é uma divergência deliberada — registre-a em `docs/decisions.md`, não a deixe silenciosa.

`follow_up_tasks`: `id`, `organizationId` (notNull), `leadId` (notNull), `title` (notNull), `dueAt` (`timestamptz`, notNull), `completedAt` (`timestamptz`, nullable), `completedBy` (`uuid`, nullable), `assignedTo` (`uuid`, nullable), `createdBy` (`uuid`, nullable), `createdAt`, `updatedAt`.
Sem coluna `status`: ele é derivado de `completedAt` e `dueAt`, como o spec B2 pede. Deixe isso escrito em comentário para ninguém adicionar a coluna depois.

**`createdBy`, `completedBy` e `assignedTo` não são FK simples para `users.id`.** Todas as três são FK **composta** com `organizationId` contra `memberships (organizationId, userId)`, como descrito no Step 2. Uma FK simples para `users.id` deixaria gravar um usuário da organização B como autor de uma atividade da organização A: a identidade vazaria entre tenants pelo histórico, sem nenhuma constraint barrando. É o item 7 do Review Focus.

- [ ] **Step 2: Adicionar as constraints de integridade**

No bloco de configuração extra de cada tabela:

- `leads`: `unique('leads_org_id_unique').on(organizationId, id)` — alvo das FKs compostas.
- `leads`: `unique('leads_org_phone_unique').on(organizationId, phone)`. **Decisão tomada:** adotar. Dois leads com o mesmo telefone na mesma organização são a mesma pessoa, e o funil ficaria ambíguo; organizações diferentes podem ter o mesmo telefone sem conflito. Registre em `docs/decisions.md` (o spec B2 pede essa decisão explicitamente).
- `activities` e `follow_up_tasks`: `foreignKey({ columns: [organizationId, leadId], foreignColumns: [leads.organizationId, leads.id] })` com `onDelete: 'cascade'`.
- **FKs compostas contra `memberships`**, todas com a forma
  `foreignKey({ columns: [organizationId, <coluna>], foreignColumns: [memberships.organizationId, memberships.userId] })`:
  `leads.assignedTo`, `activities.createdBy`, `follow_up_tasks.assignedTo`, `follow_up_tasks.createdBy`, `follow_up_tasks.completedBy`.
  É isto que garante, **no banco**, que quem é atribuído ou registrado como autor é membro da mesma organização (spec B2 para `assignedTo`; item 7 do Review Focus para os outros). As cinco colunas são nullable, então o Postgres aplica `MATCH SIMPLE`: nulo passa, preenchido só passa se existir a membership daquela organização.
- **Nenhuma dessas cinco FKs declara `onDelete`** — ficam em `NO ACTION`, deliberadamente. `ON DELETE SET NULL` em FK multicoluna anularia **todas** as colunas da FK, e `organization_id` é `NOT NULL`, então não serve (a sintaxe `SET NULL (coluna)` do PG 15+ não é exposta pelo drizzle 0.45.4). A consequência é que apagar um `user` ou uma `membership` com leads atribuídos **falha**, e isso é o comportamento desejado: a v1 não apaga `users` nem `memberships` — desligar um membro é mudar o estado da membership. Registre em `docs/decisions.md` e anote o caso "exclusão real de usuário" em `docs/backlog.md`.

Índices (spec B2):

- `index('leads_org_status_idx').on(organizationId, status)`
- `index('leads_org_phone_idx').on(organizationId, phone)`
- `index('follow_up_tasks_org_due_idx').on(organizationId, dueAt).where(sql\`completed_at is null\`)` — índice parcial. **Verificado:** `.where(condition: SQL)` existe no builder de `index()` do `drizzle-orm@0.45.4` instalado (`node_modules/drizzle-orm/pg-core/indexes.d.ts:67`), então use este caminho. Não emita `CREATE INDEX ... WHERE` como SQL cru: um índice que não está no schema TypeScript aparece como não-declarado em todo `db:generate` futuro, e o drizzle-kit pode propor dropá-lo.
- `index('activities_org_lead_created_idx').on(organizationId, leadId, createdAt.desc())` — não está na lista do spec, mas é a consulta mais quente da B4/B5 (`GET /leads/:id` com o histórico). Acrescente junto com os três obrigatórios.
